# 数据库设计（第二阶段）

## 设计原则

系统保留问卷草稿、发布快照和答卷的职责，再增加题库、逻辑题目、题目版本三个集合。问卷题目仍嵌入整份问卷，便于按题序读取和保存；题库题目独立存储，才能在多个问卷间复用并追踪版本。题库与问卷之间采用“复制内容 + 保存来源 ID”，避免普通版本切换意外改变历史答卷。

## 七个集合

| 集合 | 主要字段 | 作用 |
|---|---|---|
| users | _id、username、passwordHash、createdAt、updatedAt | 账号及注册时间；密码只保存 bcrypt 哈希 |
| surveys | _id、ownerId、publicId、title、description、allowAnonymous、allowMultiple、deadline、status、draftQuestions、draftBaseVersionId、publishedVersionId、时间字段 | 问卷元数据与当前可编辑题目数组；status 为 draft、published 或 closed |
| survey_versions | _id、surveyId、version、questions、publishedAt、publishedBy | 每次发布形成独立快照；历史 questions 不覆盖 |
| responses | _id、surveyId、versionId、respondentId、respondentKey、dedupeKey、anonymous、clientSubmissionId、answers、path、submittedAt | 每份答卷独立存储，并绑定作答时的问卷版本 |
| question_banks | _id、ownerId、name、时间字段 | 用户创建的命名题库；默认题库无需文档 |
| library_questions | _id、ownerId、bankId、currentVersionId、originRefs、shareTokenHash、archivedAt、时间字段 | 逻辑题目的稳定身份、所在题库、默认版本、母本来源、分享链接哈希和归档状态 |
| question_versions | _id、questionId、version、content、sourceVersionId、contentRevision、contentHistory、createdBy、createdAt | 题目内容的各版本；覆盖前内容保留在修订历史中 |

兼容旧数据：旧 library_questions 中的 sharedWith 字段仍可存在，但当前链接分享不使用它；旧问卷题可以没有题库来源字段，无需强制迁移。

## 嵌套、引用与身份

surveys.draftQuestions 和 survey_versions.questions 都是题目数组。每题有本卷内 qid、type、title、required，以及按题型出现的 options、validation 和 jumpRules。选项为 id/text；跳转规则包含 when 与 targetQid。qid 只在所属问卷内标识位置、答案及跳转目标。

问卷题可另存 libraryQuestionId、questionVersionId 和 contentRevision。三者分别标识逻辑题、选入的题目版本、该版本当时的内容修订；不能把它们与 qid 或问卷发布快照 ID 混用。选题只复制题干、题型、选项和校验配置，旧问卷的跳转目标不会继承。

题库的 bankId 为 null 时显示在默认题库。批量“删除”设置 archivedAt，列表隐藏，但已选入问卷的题目与历史答卷保留。分享只在数据库保存随机令牌的 SHA-256 哈希；导入时创建接收者自己的 library_questions 和 question_versions 文档，因此跨用户不会共享后续修改或统计。

存入题库的原问卷题也视作一次使用：草稿写入来源 ID，内容一致且可确认的既有发布快照通过 originRefs 记录快照 ID、qid 和题目版本 ID；不修改旧快照及答卷，也不凭题干相同推定其他历史问卷的归属。答卷独立存储，避免多人提交时不断改写问卷文档。

## 版本与查询效率

创建题目新版本时插入新的 question_versions，并更新 currentVersionId；选择某旧版为默认只更新该指针。明确覆盖指定版本时提高 contentRevision，把被覆盖内容写入 contentHistory；本人当前仍使用它的已发布问卷通过新增 survey_versions 快照承接变化，旧答卷仍绑定旧快照。跨问卷统计按题目版本和内容修订分组，防止不同题意直接混算。

| 集合 | 关键索引 | 目的 |
|---|---|---|
| users | username 唯一 | 阻止重名账号 |
| surveys | publicId 唯一；ownerId + createdAt；draftQuestions.libraryQuestionId | 公开链接、我的问卷、题目使用查询 |
| survey_versions | surveyId + version 唯一；questions.libraryQuestionId | 版本号约束及已发布使用查询 |
| responses | surveyId + respondentKey + clientSubmissionId 唯一；dedupeKey 唯一部分索引；surveyId + versionId + submittedAt + _id | 幂等、防重复和版本统计 |
| question_banks | ownerId + name 唯一 | 同用户题库名称不重复 |
| library_questions | ownerId + bankId + createdAt；shareTokenHash 唯一部分索引 | 所有者题库列表和令牌定位 |
| question_versions | questionId + version 唯一 | 查询历史、约束版本号 |

初始化脚本可重复运行，对七个集合设置 MongoDB $jsonSchema，限制必要字段和 BSON 类型；API 入口另用 Zod 校验请求，发布时检查跨题跳转。当前没有 status + deadline 复合索引，截止日期靠启动、定时任务和相关请求核对。

## 为什么适合 MongoDB

单选、多选、文本、数字及评分题使用不同的选项和校验参数；跳转条件也可能是选项集合或数字区间。文档模型可直接把这类结构放在题目文档中，整卷读取无需把题目、选项、限制和规则分散到许多关系表再拼接。受控冗余换来发布快照与历史答卷稳定；代价是题库覆盖涉及多文档协调，且单份问卷及聚合结果受 MongoDB 文档大小限制。
